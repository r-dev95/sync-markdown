# Markdown 変換アーキテクチャ

GFM、Zenn、Qiita の Markdown を相互に扱うツールを作る。本文は全体を正規表現で置換するのではなく、`remark` と `mdast` で解析してノード単位で変換する。フロントマターは本文と分離し、YAML を基準に扱う。GFM を共通のハブにすることで、各プラットフォームは GFM との直接変換に限定する。

## 決定事項

- `GFM` を共通のハブにする。
- 各プラットフォームは `GFM <-> Zenn` と `GFM <-> Qiita` の直接変換を持つ。
- 本文とフロントマターを別レイヤーとして扱う。
- 本文は `remark` / `mdast` で解析して変換する。
- 本文の変換は文字列の全体置換ではなく、ノード単位で行う。
- 未対応の本文要素は壊さず、そのまま通す。
- 変換の過程で情報が落ちることを許容する。
- 情報落ちや未対応の内容は、プログラムの警告ではなく、変換表や説明ドキュメントに記載する。
- フロントマターは YAML を基準にする。
- 意味が同じキーは可能な範囲で対応付ける。
- 変換先に存在しないキーは破棄する。
- フロントマターのキー順は、各プラットフォームの公式に従う。
- 出力は変換先の公式に寄せた canonical な形に整形する。
- `core` を独立させ、CLI と GitHub Actions は薄いラッパーにする。
- CLI を主要な利用手段にする。
- 単一ファイルとディレクトリ一括処理の両方をサポートする。
- デフォルトは別出力とし、上書きは明示オプションにする。
- 入力形式と出力形式は `--from` / `--to` のように明示指定する。
- 変換ロジックはノード種別ごと、プラットフォームごとに分割する。
- 最初は主要な Markdown ノードを優先し、Zenn / Qiita 独自要素は後から追加する。
- テストは AST レベルのユニットテストを主軸にし、スナップショットテストを補助にする。

## 理由

目的は、コードブロックのような壊してはいけない領域を含めて、安全に Markdown を変換できるようにすること。GFM を共通の基準にすると設計が単純になり、AST ベースの本文変換にすると、平台ごとの差分を局所的に扱える。

## 影響

- 初期版は分かりやすく保守しやすい一方で、Zenn / Qiita のすべての細かな差分を最初から網羅するわけではない。
- Zenn から Qiita への直接変換は第一級の経路にせず、GFM を経由する。
- 変換は一部ロスレスではないため、挙動の説明は実装だけでなくドキュメントも契約の一部になる。
- 将来的に双方向の拡張をしても、プラットフォームごとのルールが分離されているため拡張しやすい。
